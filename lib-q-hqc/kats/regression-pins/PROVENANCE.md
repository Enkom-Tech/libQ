# HQC KEM KAT provenance

**This tree is a regression pin, not a copy of an external reference vector set.** The `.rsp`
response values below were produced by running `lib-q-hqc`'s own `keygen_with_seed` /
`encapsulate_with_m_salt` / `decapsulate` against the NIST `.req` seed chain, and committed as a
fixed expected output (`tests/nist_kem_kat.rs`). A green `nist_kem_kat` test run proves this
crate's output has not changed since that commit; it does **not** prove the output matches the
official HQC reference implementation. Genuine upstream conformance is separate, unresolved work
(see `../README.md`, and the "Known divergence" section below for a public-key wire-length
mismatch this comparison already surfaced) — do not cite this tree as evidence of HQC conformance.

## Source

| Artifact | Origin |

| `hqc-*/PQCkemKAT_*_regression_pin.rsp` | **Self-generated by `lib-q-hqc`** (see `tests/nist_kem_kat.rs::write_regression_pin_rsp_file` / `regenerate_regression_pin_rsp_files`) for the **Oct 2024 / current** parameter set (`PUBLIC_KEY_BYTES` = 2241 / 4522 / 7245, `seed_ek ‖ s` PK, SHA3 `H`=1 / `G`=0, XOF KEM `seedKEM` flow). These are this crate's own output, not NIST or upstream HQC response data. |

Specification alignment: [HQC specifications (2025-08-22)](https://pqc-hqc.org/doc/hqc_specifications_2025_08_22.pdf), parameter table on [pqc-hqc.org](https://pqc-hqc.org/).

## Known divergence from the official HQC v5.0.0 reference implementation

A same-seed byte comparison against the official HQC v5.0.0 (2025-08-22) reference implementation
(`reference/hqc/kats/ref/hqc-{1,3,5}/`, untracked local checkout) shows HQC-192 and HQC-256 `pk`/
`sk` differ in **length**, not just value, from the official `api.h` constants:

| Set | field | libQ (this crate) | official reference | delta |
|-----|-------|-------------------:|--------------------:|------:|
| hqc-3 (HQC-192) | pk | 4522 | 4514 | +8 |
| hqc-5 (HQC-256) | pk | 7245 | 7237 | +8 |
| hqc-1 (HQC-128) | sk | 2289 | 2321 | -32 |
| hqc-3 (HQC-192) | sk | 4570 | 4602 | -32 |
| hqc-5 (HQC-256) | sk | 7293 | 7333 | -40 |

`ct`/`ss` match in length (differ only in value, consistent with the different RNG path below).
HQC-128 `pk` matches (2241 = 2241). This is a wire-format question tracked outside this lane
(changing a published constant is out of scope for a KAT-provenance fix); it is recorded here so
the divergence is not silently reintroduced by a future regeneration. Do not treat this tree's
byte values as evidence that libQ's HQC-192/256 wire format is correct.

## RNG path (A1)

Keygen and encaps in `lib-q-hqc` use the **SHAKE256 XOF / PRNG** path (`keygen_with_seed`,
`encapsulate_with_m_salt`), not NIST AES-256-CTR-DRBG over the record seed. This means even where
lengths agree (HQC-128), this tree's `pk`/`ct`/`ss`/`sk` **values** are not expected to reproduce
the official reference's values for the same seed — no comparison in this file establishes that
they do or don't; see "Known divergence" above for the one comparison actually run.

Older NIST submission `.rsp` files used a **2249-byte** public key layout; this tree uses the Oct 2024 **2241-byte** `pk` wire format.

## Seed-chain note

`hqc-1/PQCkemKAT_2321.req` uses a **different** seed chain (count=0 seed `061550234D158C5E...`)
than `hqc-3/PQCkemKAT_4602.req` and `hqc-5/PQCkemKAT_7333.req`, which share one chain (count=0 seed
`9EF877FDDBE8891C...` — this is also the official reference's chain). This asymmetry is inherited
from how these `.req` files were vendored; it is not a defect in the response data (each `.rsp` is
still self-consistent with its own `.req`), but it means hqc-1 cannot be directly diffed against
the other two sets using a shared seed. Not investigated further by this lane.

## Regeneration

Maintainers may refresh the self-generated `.rsp` files (not CI-gated; this only re-runs this
crate's own code against itself, it does not fetch or check anything external) with:

```bash
cargo test -p lib-q-hqc --release --features "alloc,hqc,random" \
  --test nist_kem_kat regenerate_regression_pin_rsp_files -- --ignored
```
